# Working rules

- Work autonomously through implementation and verification; choose routine details yourself and ask only when essential information or a consequential decision cannot be inferred.
- Correctness, reliability and maintainability first. Inspect the relevant code and existing changes, keep the scope focused, preserve unrelated work and user data. Check every premise, yours or given, against the code (`origin/main` after a fetch if the checkout may be behind), a measurement or its source.
- Verify the requested and affected behavior with fitting checks, add regression tests where useful, review the final diff, and report what stayed unverified.
- Commit only the task's changes with a specific conventional message and land them on remote `main` (Orca worktree branches too) unless the user asks otherwise: `python "$HOME/.claude/tools/land.py" --repo <checkout> --check "<affected checks>"` rebases, runs the check (PowerShell on Windows) only if the rebase brought changes, asks the review hook and pushes; when it stops it says what to do. Give it a long timeout or the background when the check takes minutes; `--watch` adds CI (`--ci <sha>` later). Without it: fetch, rebase onto `origin/main`, re-run affected checks if the rebase brought changes, `git push origin HEAD:main`. Report access or branch-protection blockers.
- Never commit secrets, force-push, rewrite shared history, open PRs, tag or publish releases unless explicitly asked.
- Keep context lean and turns few: every turn re-reads all of it. Batch independent reads and searches in one turn, search before reading, read only the ranges needed, filter output to counts, errors and tails, send long logs to a file and grep it, never re-read what you hold, and start a fresh session for an unrelated topic.
- Where `scout`, `runner` or `mechanic` helper agents exist, delegate broad searches to `scout`, builds, test suites and long CI waits to `runner`, fully specified multi-file edits to `mechanic`. Do one- or two-call work and anything needing judgment yourself; make uniform bulk changes with a script.
- Where Orca and OpenCode are installed and you run on a costlier model, give volume work to a near-free DeepSeek worker so only its report enters your context: reading a subsystem or over about 1,000 lines, scaffolding (boilerplate, test skeletons, repetitive first drafts) and translation (UI strings, help texts, docs), written to disk and reported by path. Before briefing an implementation agent on code you have not mapped, have DeepSeek map where the change lands and put its `path:line` report in the brief as a starting point, not the full list of call sites. Start it per the `orchestration` skill: `orca orchestration worker-start --agent opencode --model opencode-go/deepseek-v4.1-flash --worktree current --spec-file <brief>`; as a subagent or for an answer in the same turn, `python "$HOME/.claude/tools/deepseek.py" read "<brief>"` (or `write`) blocks and prints only the report. Keep design, debugging, safety-critical code and small reads yourself, read the exact range yourself before editing it, review its output as part of your diff (translations: keys, placeholders and markup intact, one language you can judge read through), and never dispatch from inside a worker.
- Subagents never run on the costliest model; in Claude Code they default to Opus: never pass a costlier `model`, pass `sonnet` or `haiku` for simple, well-specified work, and on the costliest model brief a fresh agent instead of a `fork`.
- As an Opus main chat with an `advisor` tool, consult it on the choices of any task that changes behaviour: before committing to an approach (what to build, how far, which default, what to measure), when a fix failed, and before declaring done once the result is saved; not every turn. Weigh it against your evidence and report where you departed. Subagents and chats on the advisor's own model do not call it.
- Where a `reviewer` agent exists, have it check a code change of over about 60 lines before landing: give it the repository, the whole range since `origin/main`, the user's request in their words and the path of any vendor SDK called; fix its findings and ask again only after a High finding or over about 150 lines of fixes. A hook holds an unreviewed push to `main`; if the user asked for speed, pass `land.py --skip "<reason>"` or end the push command with `# REVIEW_SKIP=<reason>`. Commit and push in separate commands.
- Brief a helper or worker so it need not rediscover what you know: the end state and the check that proves it, paths, constraints, an example where a pattern matters, what it may edit and when to stop. One change per brief; ask for a short report with `path:line` evidence, and tell an Orca worker to deliver it with its finish command.
- Scratch files (commit messages, scripts, logs) go in the system temp or task folder, never beside repositories; commit with `git commit -F -`. A task that builds or tests starts with `python "$HOME/.claude/tools/task.py" open <task>`, keeps its outputs in the printed folder, records what it makes elsewhere (a folder, a running process, a remote folder, a device setting) with `task.py add`, and ends with `task.py close <task>`, which undoes those and deletes the folder. Preserve deliverables, shared dependencies and active work: copy what must stay out first.
- Communicate concisely: result, consequential decisions, verification, limitations. When done, name each part of the request as done, not done (why) or not verified.
