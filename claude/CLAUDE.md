# Working rules

- Work autonomously from the request through implementation and verification. Choose routine implementation details yourself; ask only when essential information or a consequential decision cannot be inferred.
- Prioritize correctness, reliability and maintainability. Inspect relevant code and existing changes, keep the scope focused, and preserve unrelated work and user data. Before building on a premise, your own or one you were given, check it against the code (on `origin/main` after a fetch when the checkout may be behind), a measurement or its source.
- Verify the requested behavior and affected existing behavior with appropriate checks. Add regression coverage where useful, review the final diff, and report anything unverified honestly.
- For repository changes, commit only the task's changes with a specific conventional message, then land them on remote `main` unless the user requests another workflow, in one call: `python "$HOME/.claude/tools/land.py" --repo <checkout> --check "<affected checks>"` fetches, rebases onto `origin/main`, runs the check (PowerShell on Windows) only when the rebase brought in changes, asks the review hook, pushes and retries when `main` moved meanwhile; it stops on a conflict, a failed check or a hold and says what to do next. Give it a long timeout or run it in the background when the check takes minutes; `--watch` adds the commit's CI (`--ci <sha>` later). Without it: fetch, rebase onto `origin/main`, re-run affected checks if the rebase brought in changes, and `git push origin HEAD:main`. This applies on Orca worktree branches too. Preserve unrelated work; report access or branch-protection blockers.
- Never commit secrets, force-push, rewrite shared history, open PRs, tag or publish releases unless explicitly requested.
- Keep context lean and turns few; every turn re-reads all of it. Send independent reads and searches together in one turn, not one per turn. Search before reading and read only the ranges you need, filter command output to counts, errors and tails, send long logs to a file and grep it, don't re-read what you already hold, and start a fresh session for an unrelated topic.
- Where `scout`, `runner` or `mechanic` helper agents exist, delegate to them: broad searches to `scout`; builds, test suites and long CI waits to `runner`; fully specified multi-file edits to `mechanic`. Do work of one or two tool calls, and anything needing judgment, yourself. Make uniform bulk changes with a script, not edit by edit.
- Where Orca and OpenCode are installed and you run on a costlier model, hand volume work to a DeepSeek worker, which is close to free even at maximum reasoning, so that only its report enters your context: bulk reading (surveying a subsystem, or more than about 1,000 lines of files, logs or documents) and scaffolding (boilerplate, test skeletons, repetitive first drafts), which it writes to disk and reports by path. Start it per the `orchestration` skill with `orca orchestration worker-start --agent opencode --model opencode-go/deepseek-v4.1-flash --worktree current --spec-file <brief>`. Keep design, debugging, safety-critical code and small reads yourself, read the exact range yourself before editing it, review what it wrote as part of your diff, and never dispatch from inside such a worker. As a subagent, or when you need the report in the same turn, run `python "$HOME/.claude/tools/deepseek.py" read "<brief>"` (or `write`) instead: it blocks and prints only the report.
- A subagent never runs on the costliest model. In Claude Code subagents default to Opus: don't pass a costlier `model`, pass `sonnet` or `haiku` for simple, well-specified work, and on the costliest model brief a fresh agent instead of a `fork`, which runs on your own model.
- Where an `advisor` tool is available and you are an Opus main chat, consult it on the choices of any task that changes behaviour: before committing to an approach (what to build, how far, which default, what to measure), when a fix did not work, and before declaring the work done, once the result is saved. Not on every turn, since each call re-reads the whole conversation. Weigh its advice against your own evidence and report where you departed from it. As a subagent, or when the main chat runs on the advisor's own model, do not call it: a reviewer is already the independent check, and every call draws on the advisor model's weekly allowance.
- Where a `reviewer` agent exists, have it check a code change of more than about 60 lines before it lands: give it the repository, the whole range since `origin/main`, the request in the user's own words and the path of any vendor SDK the change calls, fix what it finds, and ask again only after a High finding or fixes of more than about 150 lines. A hook holds back an unreviewed push to `main`; when the user asked for speed, pass `land.py --skip "<reason>"` or end the push command with the comment `# REVIEW_SKIP=<reason>`. Commit and push in separate commands: a push command that also commits is counted by everything the checkout holds, other tasks' uncommitted work included.
- Brief a helper or worker so it need not rediscover what you know: the end state and the check that proves it, the paths and constraints, an example where a pattern matters, what it may edit, and when to stop instead of acting. One change per brief; ask for a short report with `path:line` evidence, and tell an Orca worker to deliver it with its finish command.
- Write scratch files (commit messages, helper scripts, logs) to the system temp directory or the task's artifact directory, never beside repositories; pass commit messages with `git commit -F -`. A task that builds or tests starts with `python "$HOME/.claude/tools/task.py" open <task>` and keeps every output in the folder that prints; what it makes elsewhere (a folder, a process it leaves running, a folder on another machine, a device setting) it records with `task.py add`, and it ends with `task.py close <task>`, which puts those back and deletes the folder. Preserve deliverables, shared dependencies and active work: copy what must stay out of the task folder before closing.
- Keep communication concise: result, consequential decisions, verification and remaining limitations. When reporting a task done, name each part of the request as done, not done (with the reason) or not verified.
