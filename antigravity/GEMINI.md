# Global Agent Guidelines

Aim for momentum: small verified changes landed cleanly, in few turns and lean context.

- Work autonomously using Antigravity's native workflows (`/swarm`, `/teamwork`, `invoke_subagent`, `run_workflow`); ask only when a consequential decision cannot be inferred. Run directly on `Gemini 4 Neon` (High/XHigh) — never `Orchestrator (Neon)` for coding, since its Flash executor introduces subtle bugs. Check premises against `origin/main`, a measurement, or official docs when a device is not local.
- Batch independent searches, reads, and edits in parallel; read only needed line ranges and filter command output to errors/tails. Keep parallel workers tightly scoped with incremental commits, and cap concurrent local Rust/Gradle builds to ≤2–3 on this PC.
- Build hygiene and zero firewall prompts: reuse shared pools (`CARGO_TARGET_DIR`, Rubylight: `python tools/dev.py cargo -- <args>`, Gradle via `tools/build_lock.py --lane gradle -- ... --no-daemon`), bind local dev/test servers to loopback (`127.0.0.1`/`localhost`/`[::1]`), and clean up private build/temp dirs and finished workers before reporting done.
- Hardware and laptop offload: on `HOMEPC`, use the `rubylight-hw` MCP tools for local display/GPU checks (`run_command` runs on a hidden `exebox-*` desktop that WGC cannot see; exit code 3 is an AMD encoder hang — investigate, never retry). To offload heavy CPU or GPU builds/tests to the laptop (`ramaz@192.168.4.12`), use `python "$HOME/.claude/tools/laptop.py" status|run|check|clean`.
- Optional cross-harness second opinion (only when explicitly requested): run `python "$HOME/.claude/tools/worker.py" <read|write|code|review> --harness claude --dir <checkout> "<brief>"`.
- Verification and git safety: verify with the narrowest fitting check, add a regression test where useful, commit only the task's changes with a conventional message, and never commit secrets, force-push, rewrite shared history, open PRs, tag, or publish unless asked.
- Public GitHub replies (issues or PRs): state what changed, when it ships, and ask the reporter to test and report back — never tell users we cannot run tests locally or lack hardware. Keep hardware-untested caveats in internal reports only and never claim unrun hardware tests as passed.
- Report concisely: result, decisions, verification, limits; mark each part of the request done, not done (why), or not verified.
